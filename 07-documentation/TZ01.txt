# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## Система лояльности для магазина одежды

### Версия 1.3 (аудит 02.09.2026)

---

# 1. Цель проекта

Разработать единую систему лояльности для сети из 4 магазинов одежды.

Система должна позволять:

* регистрировать клиентов;
* хранить единую базу клиентов;
* начислять и списывать бонусные баллы;
* разделять накопительные и подарочные баллы;
* показывать клиенту текущий баланс;
* отправлять клиентам текстовые сообщения через Telegram;
* позволять кассирам создавать операции с баллами;
* передавать начисления на подтверждение администратору;
* вести историю всех операций внутри системы;
* предоставлять администратору статистику;
* управлять правилами программы лояльности;
* в дальнейшем подключить собственную систему учёта и продаж.

На первом этапе система лояльности является самостоятельной системой.

В дальнейшем она должна иметь возможность интеграции с собственной системой учёта и кассой.

---

# 2. Общая схема системы

Система работает внутри Telegram.

Основной интерфейс клиента и администратора — Telegram Mini App.

```text
                    ┌─────────────────┐
                    │     Клиент      │
                    │    Telegram     │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │  Telegram Bot   │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │   Mini App      │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │     Backend     │
                    │ Python / Django │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │   PostgreSQL    │
                    └─────────────────┘
```

Кассир и администратор также работают через Telegram.

---

# 3. Пользовательские роли

В системе предусмотрено 3 роли:

### Клиент

Может:

* зарегистрироваться;
* посмотреть текущий баланс;
* посмотреть свои данные;
* изменить свои данные;
* посмотреть правила программы;
* получать сообщения и информацию об акциях.

### Кассир (доступ магазина)

Каждый магазин сети имеет **свой доступ в системе**. К магазину привязываются **Telegram ID** сотрудников, которые работают на этой точке.

**Единая база клиентов** (раздел 6) и **доступы магазинов** — разные вещи:
* клиенты одни на всю сеть;
* кассиры входят через Telegram ID, привязанный к конкретному магазину.

Личный именованный аккаунт «Иванов кассир» **не создаётся**. Администратор указывает Telegram ID и привязывает его к магазину.

На один магазин можно привязать **несколько Telegram ID** (несколько сотрудников одной точки).

Один Telegram ID может быть привязан **только к одному** магазину.

Кассир (оператор магазина) может:

* найти клиента;
* посмотреть текущий баланс клиента;
* создать операцию начисления;
* создать операцию списания;
* видеть результат созданной операции.

Кассир не имеет доступа к административным функциям.

При создании операции система сохраняет:

* идентификатор магазина;
* Telegram ID, с которого выполнена операция.

### Администратор

Имеет полный доступ к системе:

* клиенты;
* операции;
* подтверждение начислений;
* баллы;
* кассиры;
* настройки;
* статистика;
* рассылки.

---

# 4. Авторизация и определение роли

Авторизация пользователей осуществляется через Telegram.

У каждого пользователя определяется Telegram ID.

Backend проверяет, какая роль закреплена за данным Telegram ID.

Пример:

```text
Telegram ID → роль
```

```text
123456789 → STORE (Магазин 1)
234567890 → STORE (Магазин 2)
987654321 → ADMIN
```

Backend определяет не только роль, но и **магазин**, если роль — STORE.

После авторизации система автоматически показывает интерфейс, соответствующий роли.

Важно:

роль проверяется на backend, а не только на уровне отображения кнопок.

Даже если пользователь попытается напрямую отправить запрос к административному API, backend должен проверить его права и отказать в доступе при отсутствии необходимых разрешений.

# 5. Регистрация клиента

В магазинах размещается QR-код.

Клиент сканирует QR-код и переходит в Telegram-бот.

Сценарий:

```text
QR-код
   ↓
Telegram Bot
   ↓
Регистрация
   ↓
Mini App
   ↓
Создание клиента
```

Клиент заполняет:

* ФИО;
* номер телефона;
* email;
* дату рождения.

Перед регистрацией клиенту отображаются условия программы лояльности и необходимые согласия.

После завершения регистрации клиент становится участником программы лояльности и создаётся в общей базе.

---

# 6. Единая база клиентов

Все 4 магазина работают с **одной общей базой клиентов**.

Отдельных баз для каждого магазина не создаётся.

Клиент регистрируется один раз и после этого может совершать покупки в любом из 4 магазинов.

Все операции с его бонусами работают с единым балансом.

---

# 7. Данные клиента

В карточке клиента хранятся:

* внутренний ID;
* Telegram ID;
* ФИО;
* номер телефона;
* email;
* дата рождения;
* дата регистрации;
* накопительные баллы;
* подарочные баллы;
* общее количество баллов;
* общая сумма покупок;
* количество операций;
* статус клиента;
* дата последней операции.

Также в базе сохраняется история всех операций клиента.

История используется системой и доступна администратору.

---

# 8. Клиентский Mini App

Mini App открывается непосредственно внутри Telegram.

Отдельное приложение скачивать не требуется.

Основное меню клиента:

### Мой баланс

Клиент видит только свой текущий баланс.

Например:

```text
Накопительные баллы: 2 500
  └ Сгорят 15.10.2026: 800
  └ Сгорят 01.12.2026: 1 700

Подарочные баллы: 500
  └ Сгорят 20.09.2026: 500

Всего: 3 000 баллов

Ближайшие сгорания:
  20.09.2026 — 500 подарочных
  15.10.2026 — 800 накопительных
```

Накопительные и подарочные баллы отображаются **отдельно**.

Для каждого типа показывается:
* текущий баланс;
* **даты и суммы** баллов, которые сгорят в ближайшее время (если есть).

Общий блок «Ближайшие сгорания» показывает самые срочные по обоим типам.

Клиент **не видит историю операций**.

---

# 9. Мои данные

Клиент может посмотреть свои данные:

* ФИО;
* номер телефона;
* email;
* дату рождения.

Клиент может редактировать свои данные.

После изменения информация обновляется в общей базе клиентов.

---

# 10. Правила программы

Клиент может посмотреть актуальные правила программы лояльности.

Например:

* сколько процентов начисляется за покупку;
* сколько составляет 1 балл;
* срок действия накопительных баллов;
* срок действия подарочных баллов;
* максимальный процент оплаты покупки баллами;
* другие условия программы.

Информация отображается согласно текущим настройкам администратора.

Числовые параметры (процент, сроки, пороги, лимиты) подтягиваются из настроек **автоматически**.

Дополнительный поясняющий текст правил программы администратор редактирует **вручную** в административной панели.

---

# 11. Акции

В Mini App клиент может видеть информацию об актуальных акциях магазина.

На первом этапе предусматривается простое отображение текстовой информации об акциях.

---

# 12. Накопительные баллы

Накопительные баллы начисляются за покупки.

Например:

```text
Покупка: 10 000 ₽
Процент начисления: 5%

Начисляется:
500 баллов
```

Количество баллов рассчитывается системой автоматически.

Кассир не вводит количество баллов вручную.

---

# 13. Порог начисления

В административных настройках предусматривается параметр:

**Минимальная сумма покупки для начисления баллов.**

Например:

```text
Минимальная сумма: 1 000 ₽
```

Если сумма покупки меньше установленного значения, баллы не начисляются.

Значение может изменяться администратором.

---

# 14. Процент начисления

Администратор может самостоятельно установить процент начисления.

Например:

```text
Процент начисления: 5%
```

Расчёт:

```text
10 000 ₽ × 5% = 500 баллов
```

Если процент изменён на 10%:

```text
10 000 ₽ × 10% = 1 000 баллов
```

Изменение настройки не требует изменения программного кода.

---

# 15. Срок действия накопительных баллов

Администратор устанавливает срок действия накопительных баллов.

Например:

```text
Срок действия: 3 месяца
```

После окончания срока неиспользованные баллы становятся недействительными.

Система фиксирует факт сгорания баллов в истории операций.

---

# 16. Подарочные баллы

Подарочные баллы являются отдельным типом баллов.

Они не смешиваются с накопительными.

Например:

```text
Накопительные: 2 500
Подарочные: 1 000

Всего: 3 500
```

Подарочные баллы могут использоваться:

* за регистрацию;
* в качестве подарка;
* в рамках акции;
* в качестве персонального бонуса;
* на день рождения.

---

# 17. Срок действия подарочных баллов

Для подарочных баллов устанавливается отдельный срок действия.

Например:

```text
Подарочные баллы: 1 000
Срок действия: 30 дней
```

Срок устанавливается администратором.

---

# 18. Максимальное списание баллов

Администратор устанавливает максимальный процент покупки, который можно оплатить баллами.

Например:

```text
Максимальное списание: 30%
```

Если покупка составляет:

```text
10 000 ₽
```

максимально можно списать:

```text
3 000 баллов
```

Система автоматически рассчитывает допустимый лимит.

Кассир не сможет провести списание выше установленного ограничения.

---

# 19. Начисление баллов кассиром

Кассир работает через Telegram ID, привязанный к своему магазину (см. раздел 30).

Сценарий (по шагам):

### Шаг 1

Кассир нажимает:

**Начислить баллы**

### Шаг 2

Вводит номер телефона клиента.

### Шаг 3

Система находит клиента.

### Шаг 4

Кассир вводит сумму покупки.

Например:

```text
10 000 ₽
```

### Шаг 5

Система автоматически рассчитывает количество баллов:

```text
10 000 × 5% = 500 баллов
```

### Шаг 6

Операция отправляется администратору на подтверждение.

---

# 20. Подтверждение начисления администратором

Начисление не зачисляется клиенту сразу.

После создания операции она получает статус:

```text
PENDING
```

То есть:

**Ожидает подтверждения.**

В административной панели отображается:

```text
Клиент: Иван Иванов
Телефон: +7...
Магазин: Магазин 1 (ул. Примерная, 10)
Telegram ID оператора: 123456789
Дата: 22.08.2026
Время: 14:35

Сумма покупки: 10 000 ₽
Начислено: 500 баллов

Статус:
Ожидает подтверждения
```

Администратор может:

### Подтвердить

Операция получает статус:

```text
CONFIRMED
```

Баллы зачисляются клиенту.

### Отклонить

Операция получает статус:

```text
REJECTED
```

Баллы клиенту не начисляются.

---

# 21. Список операций на подтверждение

В административной панели создаётся отдельный раздел:

**Ожидают подтверждения**

В нём находятся все операции, которые ещё не обработал администратор.

Например:

```text
Ожидают подтверждения: 37
```

Если администратор не заходит каждый день, операции продолжают накапливаться.

Он может зайти через несколько дней и обработать их все.

---

# 22. Данные операции

Для каждой операции отображаются:

* дата;
* время;
* клиент;
* номер телефона;
* сумма покупки;
* количество начисляемых баллов;
* тип баллов;
* магазин (источник операции);
* Telegram ID оператора;
* статус операции.

---

# 23. Редактирование операции администратором

До подтверждения администратор может изменить:

* сумму покупки;
* количество начисляемых баллов.

При изменении суммы система автоматически пересчитывает количество баллов согласно установленному проценту.

Например:

```text
Было:

10 000 ₽
500 баллов

Изменено:

8 000 ₽
400 баллов
```

После подтверждения операция считается завершённой.

---

# 24. Списание баллов

Кассир может создать операцию списания баллов.

Сценарий (по шагам):

1. найти клиента (по телефону);
2. выбрать «Списать баллы»;
3. указать сумму покупки;
4. система автоматически рассчитывает:
   * максимально допустимое списание по проценту покупки;
   * доступный баланс клиента (с учётом сроков действия);
   * итоговую сумму списания по правилу FIFO;
5. кассир **не вводит количество баллов вручную** — система списывает автоматически:
   * если баллов меньше лимита — списываются **все доступные**;
   * если баллов больше лимита — списывается **только рассчитанный максимум**;
6. кассир подтверждает операцию;
7. операция проводится.

Перед подтверждением кассир видит preview: сумма покупки, сколько будет списано, остаток баллов.

Система проверяет:

* наличие баллов;
* доступный баланс;
* срок действия;
* максимальный процент оплаты;
* другие ограничения программы.

---

# 25. Порядок использования баллов

Накопительные и подарочные баллы учитываются отдельно.

При списании система использует правило **FIFO по сроку жизни**:

**сначала списываются баллы, у которых срок действия заканчивается раньше**, независимо от типа (накопительные / подарочные), если иное не задано настройками программы.

Это позволяет сначала использовать баллы, которые скоро сгорят.

# 30. Магазины и доступы кассиров

### Магазины

В системе ведётся справочник магазинов сети Q Premium.

По умолчанию — 4 магазина. Администратор может добавлять новые (5, 6 и т.д.).

Для каждого магазина хранится:
* название / адрес;
* статус (активен / заблокирован).

### Привязка Telegram ID кассиров

Администратор в разделе **«Магазины»** (или «Кассиры») может:

* создать магазин;
* изменить название или адрес;
* **добавить Telegram ID** сотрудника и привязать его к магазину;
* добавить **несколько Telegram ID** к одному магазину (несколько кассиров одной точки);
* изменить или удалить привязку;
* заблокировать доступ.

Личные профили кассиров (ФИО, логин, пароль) **не создаются**. Идентификация — только через Telegram ID.

### Как система определяет магазин

При входе кассира в Mini App:

```text
Telegram ID
   ↓
Поиск привязки в базе
   ↓
Магазин + роль STORE
   ↓
Доступ к операциям этого магазина
```

Если Telegram ID не привязан ни к одному магазину — доступ запрещён.

### Что сохраняется в операции

Каждая операция кассира сохраняет:
* **идентификатор магазина**;
* **название/адрес магазина**;
* **Telegram ID**, с которого выполнена операция.

Это позволяет администратору видеть, **кто и из какого магазина** создал операцию.

---

# 31. Администраторы

Администратор имеет полный доступ к системе.

Его Telegram ID связывается с ролью:

```text
ADMIN
```

### Управление администраторами

В разделе **«Настройки» → «Администраторы»** главный администратор может:

* добавить нового администратора (указать Telegram ID);
* активировать или заблокировать доступ;
* удалить администратора (кроме последнего активного).

Минимум один активный администратор в системе должен оставаться.

При добавлении администратора указывается Telegram ID. После привязки пользователь получает доступ ко всем разделам админ-панели.

# 32. Статистика

Администратор может выбрать период:

* неделя;
* месяц;
* год;
* произвольный период.

Система показывает базовую статистику.

### Клиенты

* общее количество клиентов;
* новые клиенты за выбранный период.

### Покупки

* количество операций покупок;
* общая сумма покупок.

### Баллы

* начисленные накопительные;
* списанные накопительные;
* сгоревшие накопительные;
* выданные подарочные;
* использованные подарочные;
* общее количество баллов.

# 33. Рассылки

Администратор может отправлять клиентам текстовые сообщения через Telegram.

Например:

или:

> У нас началась новая акция. Ждём вас в магазине!

На первом этапе рассылки поддерживают **только текстовые сообщения**.

# 34. День рождения клиента

Дата рождения хранится в карточке клиента.

В день рождения система **автоматически**:

1. начисляет клиенту подарочные баллы (количество задаётся в настройках программы);
2. отправляет поздравление в Telegram.

Текст поздравления **редактируется администратором** в административной панели (шаблон сообщения).

Например:

```text
🎂 Поздравляем с днём рождения!

Вам начислено 1 000 подарочных баллов.
```

Факт автоматического начисления фиксируется в истории операций.

# 35. Настройки программы

Все основные правила программы должны изменяться из административной панели.

Например:

```text
Процент начисления: 5%

Максимальное списание: 30%

Минимальная сумма покупки: 1 000 ₽

Срок накопительных баллов: 3 месяца

Баллы за регистрацию: 500

Баллы на день рождения: 1 000

Срок подарочных баллов: 30 дней
```

Администратору не требуется обращаться к разработчику для изменения этих параметров.

Также в настройках (или рядом) доступна кнопка **«Скачать резервную копию»** — администратор получает файл backup на свой компьютер.

# 36. История операций

Каждая операция сохраняется в базе данных.

Основные типы операций:

```text
BONUS_ACCRUAL
BONUS_REDEMPTION
GIFT_ACCRUAL
BONUS_EXPIRATION
MANUAL_ADJUSTMENT
```

Для каждой операции сохраняются:

* уникальный ID;
* клиент;
* тип операции;
* сумма покупки;
* количество баллов;
* тип баллов;
* дата;
* время;
* статус;
* комментарий;
* источник операции.

---

# 37. Статусы операций

Основные статусы:

```text
PENDING
CONFIRMED
REJECTED
CANCELLED
```

Для начисления:

```text
PENDING
     ↓
CONFIRMED
```

или:

```text
PENDING
     ↓
REJECTED
```

Операции не удаляются из базы после завершения.

---

# 38. Защита от повторного начисления

Система должна предотвращать случайное двойное начисление.

Например, если из-за двойного нажатия кнопки один запрос отправился дважды, клиент не должен получить двойные баллы.

Для этого используются:

* уникальный ID операции;
* проверка текущего статуса;
* транзакции базы данных;
* защита от повторной обработки одного запроса.

---

# 39. Корректировка баллов

Баланс клиента нельзя просто менять напрямую без сохранения причины.

При необходимости корректировки создаётся отдельная операция.

Например:

```text
Было начислено:
+500

Ошибка.

Создаётся корректировка:
-500
```

Таким образом сохраняется история изменений баланса.

```text
       ↓
```


Это позволит в будущем подключить собственную систему учёта без необходимости полностью переписывать систему лояльности.

# 53. Резервное копирование базы данных

Резервное копирование PostgreSQL выполняется автоматически на VPS.

### Автоматическое резервное копирование

Система каждый день (1 раз в сутки) автоматически создаёт резервную копию базы данных на сервере (VPS):

```text
PostgreSQL
    ↓
Backup
    ↓
backup_2026-08-22.sql.gz
```

Файл резервной копии содержит данные базы в формате, из которого её можно восстановить.

Копии сохраняются на VPS в отдельной директории.

### Скачивание резервной копии администратором

В административной панели предусматривается кнопка:

**«Скачать резервную копию»**

При нажатии администратор получает актуальный файл резервной копии на свой компьютер.

Отдельная сложная система автоматической передачи файлов на компьютер клиента не разрабатывается.

Доступ к скачиванию имеет только администратор.

### Хранение на VPS

На сервере хранятся последние резервные копии, например:

```text
VPS
  ├── backup за сегодня
  ├── backup за вчера
  └── backup за предыдущие дни (до 7 дней)
```

Старые копии удаляются автоматически по истечении срока хранения.

Администратор может периодически нажимать «Скачать резервную копию» и сохранять файлы у себя локально.

### Период хранения на VPS

Например:

* ежедневные копии — последние 7 дней.

Конкретный срок хранения определяется перед запуском.

### Восстановление

При необходимости база может быть восстановлена из резервной копии:

```text
Backup
  ↓
PostgreSQL
  ↓
Восстановленная база
```

Необходимо один раз проверить, что резервная копия действительно восстанавливается.

Просто наличие файлов backup не гарантирует возможность восстановления.

При необходимости тексты сообщений могут быть изменены на этапе настройки проекта.

# 56. Сгорание баллов

Система должна автоматически определять баллы, срок действия которых закончился.

Например:

```text
Баллы начислены:
01.05

Срок действия:
3 месяца

Дата окончания:
01.08
```

После окончания срока баллы становятся недействительными.

Факт сгорания фиксируется в истории операций.

---

# 57. Логика баллов

В системе:

```text
1 балл = 1 ₽
```

Баллы используются только в рамках программы лояльности.

Накопительные и подарочные баллы учитываются отдельно.

---

# 58. Ограничение 30%

Например:

```text
Стоимость покупки: 20 000 ₽

Максимальное списание:
20 000 × 30%

= 6 000 баллов
```

Если доступных баллов меньше лимита — система списывает все доступные.

Кассир **не вводит** сумму списания вручную.

После реализации магазин получает единую систему, в которой:

* баллы рассчитываются автоматически;

* администратор может подтвердить, отклонить или исправить операцию;
* есть ограничения на списание и сроки действия баллов;
* администратор управляет правилами и текстом программы;
* администратор видит статистику и делает текстовые рассылки;
* система сохраняет полную историю операций;
* ежедневный backup на VPS и кнопка «Скачать резервную копию»;
* данные защищены разграничением ролей;
* архитектура позволяет подключить собственную систему учёта и продаж.
