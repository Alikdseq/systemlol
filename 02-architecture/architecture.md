## 2. Границы системы

```
Входит:
- сервер лояльности (клиенты, счета, операции)
- веб: рабочее место кассира + админка
- справочник 4 магазинов, пользователи (кассир/админ)
- правило начисления как настройка, не хардкод 1:1 чека

Не входит:
- фискальная касса, номенклатура, остатки, эквайринг (остаются в 1С)
- приложение покупателя, SMS-рассылка
- доработка конфигурации 1С

Этап 1 не делает:
- обмен с 1С
- офлайн-касса
- сгорание бонусов, уровни, возврат-автомат
- публичный self-signup покупателя
```

## 3. Варианты

### Вариант A — отдельный сервис лояльности, без 1С (этап 1)

```
Суть: Django (ориентир контура офиса) + PostgreSQL + веб кассир/админ. Кассир вводит телефон и сумму чека вручную. 1С параллельно как сейчас.

Плюсы: закрывает must без доступов 1С; один контур правды по бонусам; PM может нарезать; срок короче обмена 1С.

Минусы: двойной ввод; риск рассинхрона скидки с 1С при списании.

Риск: кассиры саботируют ввод. Митигация: UI в 3 действия; инструкция «скидка 1С = списание».

Когда уместен: нет описания 1С, нужен рабочий инкремент, BA рекомендовал этот путь.
```

### Вариант B — сервис + обмен с 1С на этапе 1

```
Суть: то же ядро + обработка/обмен: закрытый чек 1С отдаёт сумму; списание пишет скидку в чек.

Плюсы: меньше ошибок суммы; ближе к «автоматически».

Минусы: конфигурация неизвестна; нужен доступ, возможно платный специалист 1С, срок непредсказуем; must блокируется чужой системой.

Риск: гадание документов 1С. Офис запрещает.

Когда уместен: CEO достал конфигурацию, тестовую базу, владельца 1С. Тогда SHOULD поднимаем в must отдельным решением CEO.
```

### Вариант C — лояльность внутри 1С

```
Суть: доработать 1С (контрагент, бонусы, отчёты).

Плюсы: один кассовый контур.

Минусы: сейчас в 1С сознательно нет клиентов; неизвестно, есть ли типовая лояльность в их конфигурации; офис не владеет контуром 1С клиента; админка «как хочет собственник» часто неудобнее отдельного UI; зависимость от лицензий/программиста 1С.

Риск: проект встанет на доступе 1С.

Когда уместен: клиент уже ведёт клиентов в 1С и просит «допилите». Здесь факт обратный.
```

## 5. Контур решения

```
Клиенты (web / mobile / admin / 1C / bot):
- Web кассир (телефон, баланс, сумма, начислить/списать)
- Web админ (клиенты, операции, магазины, пользователи, правило начисления, корректировки)
- Mobile покупателя: нет
- 1С: вне системы этапа 1, соседняя касса
- Bot: нет

Сервер: Django + Django REST Framework + Django admin можно использовать как каркас админки ИЛИ отдельный SPA. Рекомендация этапа 1: серверный Django (templates HTMX или простой Django templates) для кассы и админки — меньше движущихся частей, чем отдельный React, пока нет публичного кабинета. Если PM/Frontend сильно нужен SPA — допустимо, но это лишняя сложность без must. Trade-off: templates быстрее к QA; SPA удобнее если потом PWA кассы. Рекомендация: Django templates + одна кодовая база. Frontend-агент подключается если CEO/PM выберут SPA; иначе Backend закрывает UI по uiux spec.

Данные: PostgreSQL. Один Account на Client. Operation — append-only журнал (начисление, списание, корректировка). Store, StaffUser.

Интеграции: нет в этапе 1. Точка расширения: ingest_sale(store, amount, external_id).

Инфраструктура (предложение, не закупка): один VPS + Postgres + HTTPS. Конкретный хостер и оплата — CEO. DEV локально. Staging желателен до prod. Prod — CEO go-live.
```

## 6. Сущности и данные

```
Сущность | Зачем | Ключевые поля | Связи | Master
Store | 4 точки | id, name, code, is_active | operations | наша система
StaffUser | кассир/админ | login, role (cashier|admin), store (касса привязана к точке; админ — все) | audit | наша
Client | покупатель | phone (unique, нормализованный), created_at, is_active | 1:1 Account | наша
Account | баланс | client, balance_bonus (целое), updated_at | Client | наша
Operation | журнал | type (accrual|redeem|adjust), amount_bonus, check_amount_rub, store, staff, client, created_at, comment, idempotency_key | Client, Store, Staff | наша; баланс = сумма журнала (или баланс + журнал, сверка)
LoyaltyRule | начисление | percent_bp или rub_per_bonus; active from | — | админ; не хардкод
```

Master данных лояльности — наш сервис. Master продажи/фискального чека — 1С (вне). Не делаем двойной master продажи.

Телефон: хранить нормализованный (цифры, код страны). Поиск точный, не «все клиенты» у кассира.

ПДн: телефон, суммы операций, магазин, время.

## 7. Контракты и обмены

```
Поток | От кого | Куда | Синхрон / асинхрон | Отказ
Поиск клиента | касса UI | API/view | синхрон | «не найден» → создать
Создать клиента | касса | сервер | синхрон | дубль телефона → открыть существующего
Начислить | касса | сервер | синхрон, идемпотентный ключ | 400 если сумма ≤0; правило не задано → 423/конфиг
Списать | касса | сервер | синхрон | 409 недостаточно бонусов; 400 если N > суммы чека (правило: списание ≤ сумма чека)
История/список | админ | сервер | синхрон | 403 не админ
Корректировка | админ | сервер | синхрон | обязателен comment
1С | — | — | нет этапа 1 | n/a
```

Детали HTTP: `02-architecture/api-spec.md`.

## 8. Безопасность и доступы

```
Роли:
- cashier: поиск/создание по телефону, начисление/списание в своём магазине, видит баланс найденного клиента, не видит полный реестр и чужие точки
- admin: все магазины, реестр, корректировки, пользователи, правило начисления

Секреты (имена): SECRET_KEY, DATABASE_URL, DJANGO_ALLOWED_HOSTS. Значения не в git.

Персональные данные: телефон. HTTPS на prod. Сессии. Не логировать полный телефон в открытых логах (маскирование). Backup — DevOps + CEO на prod.

Публичный интернет: админка и касса за логином. Открытый мир без auth — запрещён.
```
